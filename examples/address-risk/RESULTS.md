"Later slashes" are each challenge's second measurement in a run, when the challenger's credit and

### What the numbers show

- **Unflattering, and the main result: at this size the dispute protocol does not pay.** Running the
  whole network in one transaction costs 154,748 gas. Claiming an answer and finalising it costs 281,361,
  181.8% of that, and the answer arrives only after the challenge window. A contract that wants this
  model's answer should call the generated `Network` (`ingots/network`, the same kernel, equal to
  the reference on every check here) and pay 154,748 gas for an answer in the same transaction, with no
  operator, bond or watcher to trust.
- **A dispute is still cheaper than a run, but not by much:** the dearest challenge costs 101,727 gas, 65.7%
  of a whole run (9.4% and 2.3% for the two MNIST models).
- **Why: the protocol's cost is nearly fixed, the network's is not.** From 1,042 to 109,386 parameters
  (105 times) the whole run grows from 154,748 to 8,219,318 gas (53 times), while `claim` grows from 230,399 to 274,284
  (1.19 times) and the dearest dispute from 101,727 to 185,003 (1.82 times). A claim is mostly storage: its
  record takes 8 slots for this model and 8 for the largest one (four, and one per committed vector).
- **Where it starts to pay (a projection, not a measurement).** Between this model and the shipped
  one the whole run grows by about 71 gas per parameter. A straight line through those two
  measurements crosses the honest path near 2,800 parameters. No model of that size was built, and
  the two models differ in more than size (14 inputs against 784), so read it as "a few thousand
  parameters", nothing finer. Below that, run the network; above it, claim and dispute.
- **What this example is then for.** It shows the pipeline on a model of a kind people do put behind a
  contract (a tabular risk score), and it gives the honest answer to "should this one use the
  arbiter": no. The arbiter, its tests and the gate are generated and checked here all the same, and
  the same commands serve a wider risk model, where the table's left columns apply.

## 3. The use, end to end: `RiskGate` on anvil

`gate_anvil.sh`: an operator claims the model's answer for two accounts' features (reference samples
0, cleared, and 6, flagged), finalises both after the window, and scores the accounts in
`RiskGate` (`ingots/consumer`, hand-written, 1,051 bytes deployed). The cleared account enters; the
flagged one and an unscored one are refused. Scoring from an open claim, scoring by anyone but the
operator, and clearing one account with the claim about another's features all revert; the script
checks each.

| Call | Gas | Calldata bytes |
|---|---|---|
| claim (cleared sample) | 230,399 | 196 |
| claim (flagged sample) | 212,910 | 196 |
| finalize (cleared sample) | 68,062 | 36 |
| finalize (flagged sample) | 50,974 | 36 |
| score A (cleared) | 93,552 | 100 |
| score B (flagged) | 93,542 | 100 |
| enter (A, cleared) | 46,989 | 4 |

So one account's standing costs the operator 357,426 gas (the second claim, its finalize and its score;
the first of each kind in a run costs more because it also sets a storage slot for the first time).
Calling `Network.classify` instead is 154,748 gas (section 2); a gate built on that call would add its own
storage write, and was not built or measured here.

The arbiter's contract tests are generated with the contract (`ingots/arbiter/src/arbiter_tests.fe`):
an honest claim survives the challenge of every one of its 50 neurons and the class challenge, and is
finalised; one false value per layer and a false class are each slashed by their own challenge; wrong
proofs, substituted vectors and malformed claims are refused, each with its own error. A three-layer
arbiter is covered by these tests and the anvil scripts, not by the Foundry fuzz suite or the mutation
run, which are tied to the two-layer arbiter (`docs/USAGE.md`, section 6).
